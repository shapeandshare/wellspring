# Phase 1 Data Model: Full Pipeline Orchestration via Metaflow

Source: `spec.md`'s Key Entities section, resolved into concrete Metaflow
constructs and `flow.py` fields per the decisions in `research.md`.

This is an **orchestration-layer** data model — it does not introduce any
new persisted file format. Every field below either already exists in
`001`'s implementation (Makefile variables, script CLI args) or is a
Metaflow framework primitive (`Parameter`, run ID, step name). No new
database, schema, or serialization format is added.

## Entity: Orchestrated run

**Maps to**: One Metaflow `Run` — created implicitly by `python flow.py
run` (a new run) or resumed by `python flow.py resume` (continues an
existing run's identity, retrying only its failed step forward).

| Field | Type | Source | Notes |
|---|---|---|---|
| `run_id` | `str` | Metaflow-assigned (e.g. `1790442611662483`) | Distinct identity per run, exactly as the spec's Key Entities requires ("has an identity distinct from other runs"). Never generated by `flow.py` itself. |
| `model` | `str` (Parameter) | `MODEL`/`DEV_MODEL` Makefile var | FR-011/SC-007: same field drives both dev-cycle and production runs — only its *value* changes between them, never the flow definition. |
| `model_commit` | `str \| None` (Parameter) | `MODEL_COMMIT` | Passthrough, unpinned-by-default exactly as today (Article I Rule 1 — no behavior change). |
| `hf_path` | `str` (Parameter, derived default) | `HF_PATH` | Shared input to both compression-search branches (FR-003) — computed once in the flow's decensoring step, read by both branches, never independently re-derived by each (which would risk divergence). |
| `optimize_parallel` | `bool` (Parameter) | `OPTIMIZE_PARALLEL` | Governs whether the run passes `--max-workers 1` to itself — see Stage entity below and `research.md` item 4. |
| `study_checkpoint_dir` | `str` (Parameter) | `STUDY_CHECKPOINT_DIR` | Directory `log_to_mlflow` reads Heretic's Optuna journal from — matches Heretic's own `--study-checkpoint-dir` default. |
| `batch_size` | `int` (Parameter) | `DEV_BATCH_SIZE` | **Added during implementation** (T016 live-QA fix) — `decensor` was silently omitting the fixed batch size, causing every automated run to pay heretic's multi-minute batch-size auto-detection benchmark. `0` (default) omits `--batch-size` entirely. |
| `llama_perplexity_bin` / `llama_cli_bin` | `str` (Parameter) | `LLAMA_PERPLEXITY` / `LLAMA_CLI` | **Added during implementation** (T026/T027 live-QA fix) — `gguf_search` was silently omitting these binary paths, which the original `optimize-gguf` Makefile recipe always passed. |
| `n_gpu_layers` | `int` (Parameter) | `LLAMA_NGL` | **Added during implementation** (same fix as above) — GPU-offload passthrough for `gguf_search`; `0` (default) omits `--n-gpu-layers` (CPU-only). |
| `good_prompts_dataset` / `good_prompts_commit` / `good_prompts_split` / `good_prompts_column` (and the `bad_prompts_*` / `good_eval_prompts_*` / `bad_eval_prompts_*` equivalents — 16 fields total) | `str` (Parameter) | `GOOD_PROMPTS_DATASET` etc. | **Added during implementation** (T016 live-QA fix) — `decensor` was silently falling back to heretic's own unpinned dataset defaults instead of this project's pinned commits (Constitution Article I provenance discipline). See `contracts/flow-cli-contract.md`'s Parameters table for the full field-by-field defaults. |

**Validation rules**: `model`/`model_commit` inherit whatever validation
`heretic`'s own CLI already performs (unchanged — this feature does not
add new input validation on top of what `001`/heretic already do).
`optimize_parallel` is a plain boolean Parameter; Metaflow's own
`Parameter` type-checking (confirmed in `research.md` item 1's citation of
the Runner API docs: "parameter values are type-checked automatically")
rejects a non-boolean value before any step runs.

**State transitions**: `pending` (flow constructed, not yet run) →
`running` (a `run`/`resume` invocation is in progress) → `completed` |
`failed` (last step's outcome) — these are Metaflow's own run-status
states, not new application state this feature introduces.

## Entity: Stage

**Maps to**: One `@step`-decorated method in `flow.py`. Four stages exist,
matching `spec.md`'s User Stories 1 and 2 exactly:

| Stage (step name) | Wraps | Hardware requirement | FR |
|---|---|---|---|
| `decensor` | `heretic` (via `scripts/heretic_automate.exp` for non-interactive dev-cycle runs, or the plain interactive `heretic` CLI for production) | None (any platform heretic itself supports) | FR-001, FR-002 |
| `log_to_mlflow` | `scripts/log_heretic_to_mlflow.py`'s `main()` | None | FR-001, FR-010 |
| `mlx_search` | `scripts/optimize_mlx.py`'s `run_study()` | **Mac/Apple-Silicon only** (FR-005) | FR-003, FR-004 |
| `gguf_search` | `scripts/optimize_gguf.py`'s `run_study()` | None (macOS or Linux, CPU or GPU — existing `GGML_CUDA` auto-detection unchanged) | FR-003, FR-004 |

A fifth, zero-work `join_searches` step is the fan-out `join` target — it
exists solely to satisfy Metaflow's graph requirement that a fan-out
(`self.next(self.mlx_search, self.gguf_search)`) be joined before
`self.end`; it does not blend the two branches' data (FR-003: "MUST NOT
blend their inputs or outputs" — the join step only records that both
finished, never merges their artifacts).

| Field | Type | Notes |
|---|---|---|
| `name` | `str` | The Metaflow step's method name — one of the five above. |
| `status` | Metaflow's own `Task` status | `pending` / `running` / `completed` / `failed` — read via `Run(...)['<step>'].task.finished`, not a new field this feature stores. |
| `output_artifact_path` | `str` | Whatever `HF_PATH`/`MLX_OUT_DIR`/`GGUF_OUT_DIR` already resolve to — unchanged from `001`. Stage entity does not introduce a new path convention. |
| `skipped_on_resume` | `bool` (derived, not stored) | True if `resume` did not re-execute this step — observable via Metaflow's own task list, matching User Story 3's Acceptance Scenario 1 ("its already-produced checkpoint is reused directly"). |
| `run_id_field` | `str` | **New for `002` — implements FR-008/SC-004.** `metaflow.current.run_id`/`.flow_name` are real, always-populated attributes inside any running step (confirmed via the installed `metaflow` package's `current` module) — not a new ID this feature invents. Two distinct wiring points, verified against actual current Makefile behavior (not assumed): (1) `mlx_search`/`gguf_search` already flow through `optimize_mlx.py`'s `_append_manifest`/`optimize_gguf.py`'s `_write_manifest_entry` (both accept an arbitrary `dict` entry today) — the `mlx_search`/`gguf_search` step bodies merge `_run_provenance_fields()` into the `entry` dict passed to `run_study()`'s existing manifest-writing call, no change to `optimize_mlx.py`/`optimize_gguf.py` themselves (preserves FR-006/FR-009). (2) `decensor` is different: confirmed by reading `Makefile` lines 508-539, the `dev-abliterate-e2e` recipe it wraps (unlike the plain `abliterate` target) does **not** call `scripts/write_manifest.py` at all today — there is no existing call to add a field to. The `decensor` step MUST therefore add a **new** `write_manifest.py --step decensor --field run_id=<...> --field flow_name=<...> --field model=<...> ...` call after the `heretic_automate.exp` subprocess succeeds, mirroring `abliterate`'s own existing manifest fields (Makefile lines 473-485) — this is new behavior for the dev-cycle path specifically, not a field added to something that already ran, and is called out explicitly here rather than glossed over. FR-009 is preserved either way: this is a field added to (or a manifest newly written alongside) the existing sidecar/manifest, never a replacement of it. |

**Validation rules**: `mlx_search`'s hardware requirement is enforced by
the guard-clause pattern verified in `research.md` item 5 — a
`platform.system() != "Darwin"` check as the first statement in the step
body, raising a named `RuntimeError` before any expensive work.

**State transitions**: A stage "may complete, fail, or be skipped on
resume because its output already exists" — this is Metaflow's own
per-task lifecycle (verified empirically in `research.md` item 3), not a
new state machine this feature builds.

## Entity: Hardware requirement

**Maps to**: A plain Python predicate function, not a Metaflow decorator
or declarative field (per the `research.md` item 5 decision to avoid a
custom `@requires_platform` decorator as unjustified complexity).

| Field | Type | Notes |
|---|---|---|
| `stage_name` | `str` | Which stage this requirement gates — currently only `mlx_search`. |
| `predicate` | `Callable[[], bool]` | `lambda: platform.system() == "Darwin"` (or equivalent named function, per Article XII's type-hygiene convention — `def _is_apple_silicon() -> bool:`). |
| `error_message` | `str` | Must name the specific unmet requirement (SC-005) — e.g. `"ERROR: mlx_search requires macOS on Apple Silicon (mlx-vlm has no CUDA/Linux backend). Use gguf_search instead."`, mirroring the existing Makefile `convert-mlx` guard's exact wording (`Makefile` lines 556-560) so operators see a consistent message whether they hit the guard via `make` or via Metaflow directly. |

**Validation rules**: The predicate MUST be evaluated before any of the
stage's actual work begins (verified achievable trivially by ordering —
`research.md` item 5). It is independent of which run or which parameters
are in play, per the spec's Key Entities definition ("independent of
which run or which parameters are in play") — it checks `platform.system()`
only, never a Parameter value.

## Entity: Entry point

**Maps to**: Two invocation surfaces of the *same* `flow.py`, per FR-001a.
Not a persisted entity — a documentation/contract concept, detailed fully
in `contracts/`.

| Field | Type | Notes |
|---|---|---|
| `kind` | `Literal["make", "metaflow-cli"]` | Which of the two sanctioned entry points was used. |
| `invocation` | `str` | e.g. `make dev-abliterate-e2e` (make entry point) or `python flow.py run --model TinyLlama/... --dev` (direct Metaflow CLI entry point). |

**Validation rules**: Both entry points MUST resolve to the identical
underlying `flow.py` — verified structurally, not by a runtime check: the
Makefile targets' recipes are the *only* place `python flow.py run ...` is
invoked with Makefile-variable-derived arguments; there is no second copy
of any step's logic anywhere in the Makefile itself post-migration (see
`contracts/makefile-wrapper-contract.md`).

## Non-entities: what this feature deliberately does NOT model

- **No new provenance/manifest field.** FR-009 is explicit that Metaflow's
  own run/step tracking is supplementary, not authoritative — this
  feature adds no new field to any `*.provenance.json` sidecar.
- **No new MLflow schema.** FR-010 requires the existing tracking
  destination continue receiving exactly what it does today — no new
  metric, param, or tag is introduced by the orchestration layer itself.
- **No new persisted "pipeline run" record beyond what Metaflow already
  keeps in `.metaflow/`.** Per `research.md` item 7, `.metaflow/` is
  git-ignored, machine-local state — not a chain-of-custody artifact this
  project's constitution governs the schema of.
