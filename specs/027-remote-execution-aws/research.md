# Research: Remote Execution on AWS (Phase A)

Every decision cites a source or is marked **unverified**. Sources were
checked on 2026-10-02.

## R1. Provisioning: boto3 directly, not SkyPilot or an IaC framework

- **Decision**: An `Ec2Sdk` wrapper around boto3 (Apache-2.0). It covers
  `run_instances`, `describe_instances` by tag, `terminate_instances` and
  Service Quotas `get_service_quota`. Blocking calls run under
  `asyncio.to_thread` (Article XVIII).
- **Rationale**: Phase A needs one instance in one cloud. Idempotency comes from
  a run tag plus `describe_instances` (FR-004). Teardown is handled by the
  instance itself (R3), so nothing needs a control plane or a state database.
  boto3 is already in the environment via Metaflow and becomes a direct,
  pinned dependency (Article II).
- **Alternatives rejected**:
  - *SkyPilot*: adds autostop and multi-cloud support, but brings a large
    dependency tree and its own state DB in `~/.sky`. Multi-cloud is out of
    scope, so Article VI applies.
  - *Terraform/CDK*: declarative infrastructure fits long-lived resources.
    Here everything is per-run and ephemeral.

## R2. Running the job: autonomous user-data, no SSH or inbound ports

- **Decision**: The launch request carries everything the job needs. A
  cloud-init user-data bootstrap of about 10 lines, generated by Python and
  never committed as a `.sh` (AGENTS §13), does the following:
  1. Arms the hard backstop (R3).
  2. Installs `uv`, Python 3.14 and `expect`.
  3. Downloads the source archive (R5).
  4. Runs `python -m wellspring remote-agent --run-id …`.

  The agent is Python (`RemoteAgentService`). It runs the allow-listed stage
  command, syncs outputs (R4) and shuts the machine down. The Mac never
  connects to the instance.
- **Rationale**: This makes FR-005 ("teardown without the Mac") structural
  rather than best-effort. It needs no key pair and no security-group ingress.
  Status comes from `describe_instances` plus a `status.json` that the agent
  writes to the storage prefix.
- **Alternatives rejected**:
  - *SSH*: needs a key pair, port 22 ingress and a live Mac session.
  - *SSM Run Command*: needs no inbound ports, but still needs the Mac to drive
    each step. It remains a possible debugging aid (the SSM agent ships on the
    image, see R6), not a requirement.
- **Secrets**: user-data is readable by anyone with `DescribeInstanceAttribute`,
  so it carries no secrets. Phase A supports public Hugging Face models only.
  Gated models are out of scope until a secret path is specified.

## R3. Guaranteed teardown

- **Decision**: three layers.
  1. The launch sets `InstanceInitiatedShutdownBehavior=terminate` and
     `DeleteOnTermination=true` on every volume, so any OS shutdown terminates
     the instance and deletes its storage.
  2. The first user-data line runs `shutdown -h +<max_minutes>`, where
     `max_minutes = floor(spend_cap_usd / hourly_usd × 60) − 3`. The 3 minutes
     cover boot: billing starts before cloud-init reaches that line. The
     backstop holds even if the agent never starts.
  3. The agent stops the machine when the job ends, or after `IDLE_MINUTES`
     (default 15) without the stage having started. It also stops the stage
     at the profile's `sync_margin_minutes` before the backstop (10 for
     `dev`/`finetune-dev`, 30 for `prod`), so the final upload of a ~66 GB
     checkpoint fits. A run that is not `completed` uploads no checkpoint.

  `remote-down` terminates by tag, for an explicit stop.
- **Rationale**: Layers 1 and 2 need nothing from the Mac and nothing from
  Python. That meets SC-002 and SC-003.
- **Billing note**: AWS's "EC2 On-Demand Instance Pricing" page states that
  Linux instances are billed per second with a 60-second minimum. "One billing
  increment" in SC-003 is therefore one second past the cap, plus
  volume-deletion lag.

## R4. Moving results: S3, an operator-supplied `s3://bucket/prefix`

- **Decision**: The agent writes outputs under
  `<storage-uri>/<run-id>/outputs/` and writes a `checksums.sha256` file last.
  It syncs the Optuna journal and logs every `SYNC_MINUTES` (default 10), and
  does a final sync before shutdown. `remote-pull` downloads to
  `<local>/<run-id>.tmp`, skipping checkpoints unless asked (spec FR-008),
  verifies every downloaded file's checksum, then renames the directory
  atomically (Article IV) and ingests (R7). Nothing in the bucket is ever
  deleted by the tool; retention is the operator's (spec FR-017).
- **Rationale**: Outputs outlive the instance, so pulling never depends on it
  being alive. Spec 024's "storage URI" concept is reused, without building
  024's dispatch backend.
- **Access**: the instance gets an operator-supplied IAM instance profile
  (`REMOTE_INSTANCE_PROFILE`, no default), scoped by the operator to that
  prefix. Article XV Rule 2's "access restricted to Red" is an operator
  attestation (`REMOTE_RED_RESTRICTED=1`). It is required for fine-tune stages
  and recorded in the manifest, because code cannot verify an IAM policy's
  intent.

## R5. Getting code onto the instance

- **Decision**: `git archive HEAD` produces a tarball, which is uploaded to
  `<storage-uri>/<run-id>/source.tar.gz`. A dirty working tree is refused,
  naming the files (Article I). The manifest records the commit.
- **Rationale**: This works for a private repo without giving the instance git
  credentials. Weights are never uploaded (FR-006); the instance downloads
  them from Hugging Face.

## R6. Machine image

- **Decision**: Resolve the AMI ID at launch from the public SSM parameter
  `/aws/service/deeplearning/ami/x86_64/base-oss-nvidia-driver-gpu-ubuntu-24.04/latest/ami-id`,
  and record the resolved ID in the manifest (FR-010).
- **Source**: AWS DLAMI developer guide, "AWS Deep Learning Base GPU AMI
  (Ubuntu 24.04)". The 20260828 release notes list G5 and G6e as supported,
  NVIDIA driver 595.91.07, default CUDA 13.2, system Python 3.12, the SSM
  agent preinstalled, and instance NVMe mounted at `/opt/dlami/nvme`.
- **Python 3.14**: installed with `uv python install 3.14`, then linked as
  `/usr/local/bin/python3.14` via `uv python find 3.14`, because the
  Makefile's `venv` target calls `python3.14`. The agent is started with
  `PYTHONPATH=src`, because `wellspring` lives under `src/`. The `uv` commands
  are **unverified on the image** until the dev rehearsal.
- **Root device**: read from `DescribeImages` (`RootDeviceName`) at launch
  rather than assumed, so the gp3 root volume replaces the image's root
  instead of adding a second disk.

## R7. Ingesting into MLflow

- **Decision**:
  - Heretic: the pulled Optuna journal goes through the existing
    `log_heretic_to_mlflow.py` (it is idempotent, keyed on the journal path).
    The new `hardware_class` tag is added in this change (FR-009).
  - Other stages: they log to an MLflow SQLite file on the instance, which
    comes back as an artifact. A new `MlflowRunCopyService` copies each run
    into the local tracking URI with its params, metrics and tags, tagged
    `remote_run_id`. A run already carrying that tag is skipped, which keeps
    the copy idempotent (SC-004).
- **Alternatives rejected**:
  - *A remote MLflow server reachable from the instance*: needs inbound
    networking to the Mac, or a hosted server.
  - *mlflow-export-import*: a new dependency for something MlflowClient
    already covers.

## R8. Quota preflight

- **Decision**: Before launch, compare the profile's vCPU count with the
  applied value of the instance family's quota minus vCPUs already running.
  A shortfall raises `QuotaInsufficientError` with all three numbers.
- **Sources**:
  - AWS "Amazon EC2 instance type quotas": the default for "Running On-Demand
    G and VT instances" is **0**, adjustable.
  - The quota code `L-DB2E81BA` appears in third-party CLI output (DevOps AI
    Toolkit, 2026-06-23). It has not been confirmed in AWS docs. The quota is
    therefore looked up by **name** through `list_service_quotas`, so a wrong
    hard-coded code cannot silently skip the check.

## R9. Profiles (FR-002)

| Profile | Type | vCPU | GPUs | Disk | On-demand $/h (us-east-1) | Stages |
|---|---|---|---|---|---|---|
| `dev` | g5.xlarge | 4 | 1× A10G (22.35 GiB usable) | 200 GB gp3 | 1.006 (doit.com) | abliterate (dev model), gguf |
| `finetune-dev` | g5.2xlarge | 8 | 1× A10G (22.35 GiB usable) | 200 GB gp3 | 1.212 (doit.com) | ft (dev model) |
| `prod` | g6e.12xlarge | 48 | 4× L40S (44.7 GiB each, ~179 GiB total) | 2× 1900 GB NVMe + 100 GB gp3 root | 10.4926 (DevZero/cloudprice listings) | abliterate, gguf |

- All prices come from third-party pricing aggregators, not the AWS Pricing
  API.
- The catalog stores each price with a `price_checked` date, and the manifest
  records the price used.
- The cap-to-runtime conversion (R3) is only as accurate as the stored price,
  so stale prices get a warning once they are more than 90 days old.
- `prod` stays a **candidate** until the dev rehearsal measures peak VRAM
  (spec FR-002).

## R10. Stage allow-list (FR-014, FR-016)

- **Decision**: `RemoteStage` is an enum: `ABLITERATE`, `GGUF`, `FT_TRACK_B`.
  Each maps to one repository command, built as an argv list and never passed
  through a shell:

  | Stage | Command |
  |---|---|
  | `ABLITERATE` | `python src/flow.py run --only_step decensor --device_map auto …`, already non-interactive through `expect` + `heretic_automate.exp`. MLflow logging for this stage happens on the Mac, from the pulled journal (R7). |
  | `GGUF` | `make gguf …` |
  | `FT_TRACK_B` | `make finetune …` |

  MLX stages have no enum member, so they cannot be requested.
- **Pinned model commit (FR-006)**: before the stage, the agent resolves
  `MODEL` (or `FT_MODEL`) at `MODEL_COMMIT` (or `main` when it is the
  Makefile's `null`) to a Hub SHA, through `huggingface_hub` in the instance's
  venv. It passes that SHA to the stage (`--model_commit` / `--revision`) and
  records it as `model_commit_resolved`. For `ft-track-b`, the SHA is recorded
  only, because `make finetune` resolves `FT_MODEL` itself.
- **Instance preflight (FR-012)**: GPU count, smallest GPU's memory
  (≥ 95 % of the profile's) and free disk under the work directory
  (≥ `work_disk_gib`). A failure ends the run as `job_failed` before any
  weights are downloaded.
- **Rationale**: Replacing the abliteration backend changes only the
  `ABLITERATE` command mapping.
